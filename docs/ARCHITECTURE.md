# Архитектура

## Принцип

Три слоя, между ними — только типы:

```
данные (src/lib/data)  →  домен (src/lib/*.ts)  →  интерфейс (src/app, src/components)
```

UI никогда не ходит в данные напрямую: он получает их из `queries.ts`, а тот
уже применяет арендатора и зону видимости роли. Когда моки заменятся базой,
изменится только `src/lib/data` — страницы останутся прежними.

## Структура

```

    team/                  сотрудники, структура компании, отчётность по часам
```

## Поток запроса

1. `proxy.ts` читает `Host`, определяет арендатора и кладёт его в заголовок
   `x-orbis-tenant`.
2. `getSession()` в layout собирает сессию: арендатор + текущий сотрудник + его
   роль и зона видимости.
3. Страница вызывает `scoped*()` из `queries.ts` — данные приходят уже
   отфильтрованными по арендатору и роли; `translator(session.locale)` и
   `formatters(session.locale)` дают язык и форматы.
4. Доступ к разделу проверяет `moduleGate(session, module, label)`: сначала
   версия продукта агентства, затем права роли. Права на действия внутри
   раздела — `allow(tenantId, role, module, action)`: кнопки «Добавить»,
   «Экспорт», «Изменить» появляются только у тех, кому можно. Именно `allow`,
   а не `can`: агентство переопределяет матрицу прав у себя в настройках,
   и проверка обязана учитывать эти переопределения.

## Замок администрирования

Настройки портала — не раздел меню, а отдельная зона ответственности.
Проверка стоит в `app/admin/layout.tsx` и работает в два шага: сначала
право роли на модуль `admin`, затем код из `Tenant.adminPasscode`. Ни одна
страница внутри замок не проверяет — оболочка общая, поэтому обойти её
прямой ссылкой нельзя.

Открытый замок живёт в cookie `orbis_admin` со значением `tenantId`, без
`maxAge`: закрылся браузер — закрылся и замок. Cookie `httpOnly`, то есть
из скриптов страницы её не прочитать и не подделать.

Смысл не в защите от взлома (её даёт аутентификация), а в разделении
ролей: менеджер работает, владелец настраивает, и случайный клик в воронку
из рабочего экрана невозможен просто потому, что этого экрана у менеджера
нет.

## Приём лидов из Meta

Агентство ведёт рекламу в кабинете Meta — Orbis ею не управляет. Его работа
начинается там, где человек оставил заявку: лид обязан оказаться в воронке
сам, без выгрузок и пересылок.

Путь целиком:

1. **Подключение страницы.** `/api/meta/connect` без параметров отправляет
   человека в Facebook. Адрес возврата у приложения Meta один на всю
   платформу, а агентства живут на поддоменах — поэтому арендатор, сотрудник
   и адрес возврата едут в подписанном `state` (`lib/meta/oauth.ts`). Возврат
   проверяет подпись, меняет код на долгоживущий токен и забирает список
   страниц. Вход отдаёт все страницы человека, нужные не все: список ждёт
   выбора в `store.metaPending`, а подключает страницу `connectMetaPageAction`.
2. **Подписка.** Подключённая страница подписывается на `leadgen` — без этого
   Meta не присылает ничего. Отказ подписки не теряет страницу: она ложится
   со статусом `needs_reconnect`, и экран прямо говорит, что лиды не пойдут.
3. **Приход.** `/api/meta/webhook` — один адрес на все агентства: запрос идёт
   от Meta, без куки и с корневого домена. Подпись считается по сырому телу
   (`X-Hub-Signature-256`), арендатор определяется по `pageId` — больше
   развести приход по агентствам не по чему.
4. **Забор данных.** Вебхук несёт только номер лида; сами поля забираются
   вторым запросом к Graph API токеном страницы.
5. **Раскладка.** Названия полей у агентств разные: одно спрашивает
   «телефон», другое — «ваш номер для связи». Соответствие задаётся в
   `/admin/meta` на каждую форму; незнакомое поле уходит в комментарий, а не
   теряется. Форма, в которой ни одно поле не разложено на телефон или почту,
   лид не создаёт — пустая карточка хуже отсутствующей.
6. **Журнал.** Каждый приход записан со статусом (`imported`, `duplicate`,
   `unknown_page`, `no_mapping`, `failed`) и причиной: это то место, куда
   смотрят, когда «лид не пришёл».

Ответ вебхука всегда 200: иначе Meta повторяет уже разобранное событие.
Защита от повтора — сам журнал. Пока нет очереди, разбор идёт прямо в
обработчике: Meta считает задержку отказом и присылает событие заново.

Секреты приложения живут только в окружении (`META_APP_ID`,
`META_APP_SECRET`, `META_VERIFY_TOKEN`) — см. `.env.example`.

## Роботы и триггеры

Автоматика воронки. Робот отвечает на вопрос «карточка встала на стадию —
что сделать», триггер на обратный: «случилось событие — куда её поставить».

Набор действий закрыт и описан данными в `automation.ts`: поставить задачу,
уведомить сотрудника, назначить звонок или встречу, сменить ответственного,
записать в историю, перевести на стадию. Закрыт нарочно — робот обязан
делать то, что портал делает на самом деле. Кнопка «отправить письмо
клиенту» там, где почты нет, — обещание, которое агентство обнаружит
невыполненным на живых заявках.

Выполнение живёт в `store.ts`, рядом с `moveCard` и `addTask`: робот — это
те же действия портала, только без человека.

- **Вход на стадию.** `runStageRobots` вызывается из `moveCard`, из
  `createLead` (новая карточка встаёт на первую стадию — это такой же
  вход) и из `convertLead`.
- **Задержка.** Робот без задержки выполняется сразу, с задержкой встаёт
  в `robotQueue`. Настоящего планировщика пока нет: созревшие разбирает
  `sweepRobots` при первом же обращении к порталу (вызов в
  `app/layout.tsx`). Когда появится очередь, вызов уходит, а `sweepRobots`
  становится её обработчиком.
- **Карточка уехала.** Отложенный робот перед выполнением сверяет стадию
  карточки со своей. Не совпала — шаг пропускается с причиной: выполнить
  его значило бы соврать о текущем состоянии.
- **Петля.** Робот «перевести на стадию» запускает роботов новой стадии, а
  те могут перевести обратно. Глубина цепочки ограничена тремя шагами, и
  обрыв записывается в журнал.
- **Триггеры.** `fireTrigger` вызывается там, где событие случается:
  создание лида и лид из рекламы (`createLead`), комментарий и дело
  (`addTimelineAction`), конвертация (`convertLead`), приём документа
  (`setDocumentStatusAction`). Одно событие в воронке ведёт на одну
  стадию: второй триггер на то же событие заменяет первый, иначе они
  спорили бы за то, куда уедет карточка.
- **Журнал.** Каждое срабатывание записано со статусом (`done`,
  `skipped`, `failed`) и причиной. Автоматика, которую не видно, —
  автоматика, которой не доверяют: журнал здесь не приложение к экрану, а
  половина его смысла.

Чего пока нет: условий у робота («сработать, только если сумма больше…»).
Робот стадии выполняется для всякой карточки, которая на неё встала.

## Что обязательно для проверки Meta

Приложение не выпускают к живым людям, пока у него нет четырёх адресов,
и все четыре — наши:

| Назначение | Адрес |
|---|---|
| Вебхук лидов | `/api/meta/webhook` |
| Возврат после входа | `/api/meta/connect` |
| Удаление данных | `/api/meta/deletion` |
| Отключение приложения | `/api/meta/deauthorize` |
| Политика конфиденциальности | `/privacy` |
| Инструкция по удалению | `/data-deletion` |

Две страницы открываются **без входа** — их читает проверяющий Meta и
человек, оставивший заявку в рекламе, а не сотрудник агентства. Поэтому
они стоят в `isPublicPath` рядом с входом и регистрацией.

Обратные вызовы подписаны иначе, чем вебхук лидов: не заголовок
`X-Hub-Signature-256`, а одна строка «подпись.тело» (`signed_request`).
Разбор и проверка — в `lib/meta/signed-request.ts`, сравнение постоянного
времени. Без проверки любой желающий стирал бы чужие подключения, присылая
чужой идентификатор.

`/api/meta/deletion` обязан вернуть JSON с полями `url` и
`confirmation_code`. HTML вместо JSON или ответ без любого из полей — отказ
на проверке. По коду человек открывает `/data-deletion?code=…` и видит, что
именно сделано.

Чтобы заявку было с чем сопоставить, `MetaPage` хранит `connectedByFbId`:
Meta присылает только идентификатор человека в рамках нашего приложения.

**Умерший токен.** Отозванный доступ нельзя оставлять под зелёной надписью
«Подключено»: лиды не идут, а понять это можно только дочитав журнал.
`importLead` отличает «доступ отозван» (коды 190, 463, 467, OAuth-ошибки)
от «Meta моргнула» и в первом случае переводит страницу в
`needs_reconnect` — на экране это красная строка, а не тишина.

## Умный фильтр

Фильтр один на весь портал. Раздел описывает свои поля (`section-filters.ts`)
и отдаёт плоскую проекцию записи — `FilterRow`; сопоставление делает одна
функция `matchesFilter(row, fields, values, query)`. Новый раздел получает
фильтр, написав только эти две вещи.

Состояние фильтра живёт в адресе страницы: `q` — поиск, `f_<ключ>` — условие
поля (у диапазонов `f_<ключ>From` и `f_<ключ>To`), `fields` — какие поля
показаны, `preset` — выбранный пресет. Поэтому страница остаётся серверной,
отфильтрованный список открывается по ссылке, а «назад» в браузере работает
как ожидается. Условия применяются по кнопке «Найти», а не на каждое нажатие
клавиши. Сохранённые наборы принадлежат сотруднику и разделу
(`savedFilters(userId, scope)`).

## Темы

Тема хранится в cookie `orbis_theme`, читается в `getSession()` и ставится
атрибутом `data-theme` на `<html>` при серверном рендере — вспышки чужой темы
нет, потому что первая же разметка приходит уже в нужной теме. Светлая —
значения по умолчанию в `@theme`, тёмная — переопределения токенов в
`:root[data-theme="dark"]`. Компоненты не знают о теме: они используют только
токены (`--color-surface-1`, `--color-hairline`, `--shadow-card`).

## Изменяемое состояние

Базы пока нет, но интерфейс должен работать по-настоящему: перенос карточки
на доске, отметка рабочего дня, переименование стадии, конвертация лида —
всё это где-то сохраняется. `src/lib/store.ts` держит состояние в памяти
процесса (`globalThis.__orbisStore`, чтобы пережить hot reload) и предоставляет
функции с теми же сигнатурами, какие позже будут у репозиториев поверх
Postgres. Мутации идут только через серверные действия из `app/actions.ts`,
и каждая значимая пишет событие в историю карточки.

## Серверное и клиентское

Серверные компоненты по умолчанию. Клиентские — только там, где нужна
интерактивность без перезагрузки: канбан с перетаскиванием, история карточки,
правка полей, настройки воронки, матрица прав, панель фильтра, календарь,
структура компании, счётчик рабочего дня, шапка и навигация. Логика подбора (`matching.ts`) — чистые функции без зависимостей,
поэтому одинаково работают и на сервере (карточка контакта), и в браузере
(живые фильтры каталога).

Собственные элементы управления живут в `components/controls.tsx`:
`Select`, `DatePicker`, `Modal`, `Tooltip`, `ColorPicker`. Нативные `<select>`
и `<input type="date">` рисует операционная система — они выглядят
чужеродно, по-разному в каждом браузере и не следуют теме портала, поэтому
в коде их нет.

## Что будет при переходе на базу

- `src/lib/data/*` → репозитории поверх Postgres (Prisma/Drizzle).
- `tenantId` остаётся обязательной колонкой во всех таблицах; политика
  изоляции — на уровне запроса и RLS.
- `queries.ts` становится сервисным слоем: те же сигнатуры, внутри SQL.
- Серверные действия из `actions.ts` вырастают в мутации с аудитом
  (кто, что и когда изменил — лента событий уже есть в модели).

## Готовность к облачному серверу

Портал собирается и запускается как обычное Next.js-приложение
(`npm run build && npm start`), но три вещи стоит знать заранее, до переезда
с локального запуска на реальный сервер:

- **`next.config.ts` → `output: "standalone"`.** Сборка кладёт в
  `.next/standalone` автономный сервер без `node_modules` — именно это
  копируется в Docker-образ. Локальный `next dev`/`next start` это не меняет.
- **`src/proxy.ts`, не `middleware.ts`.** Next 16 переименовал соглашение;
  старое имя ещё работает с предупреждением, но при обновлении фреймворка
  на сервере может быть убрано вовсе. Функция называется `proxy`, а не
  `middleware`, — при правке файла это стоит сохранить.
- **`src/lib/store.ts` живёт в памяти одного процесса.** Для одного
  контейнера этого достаточно, но на нескольких репликах или при
  бессерверном запуске (несколько холодных инстансов) правки не увидят друг
  друга — это тот же переход, что описан выше «Что будет при переходе на
  базу»: до Postgres несколько реплик поднимать нельзя, один процесс —
  можно.

Единственная переменная окружения — `NEXT_PUBLIC_ROOT_DOMAIN` (см.
`.env.example`): корневой домен платформы, из которого собираются поддомены
арендаторов. Куки, отвечающие за реальный контроль доступа (`orbis_admin`),
ставятся с `secure` только в `NODE_ENV=production` — на облачном хостинге
это HTTPS, а на `localhost` без TLS браузер такую куку просто не принял бы.
Демо-переключатели (`orbis_user`, `orbis_tenant`, `orbis_locale`) — не
граница безопасности, их заменит настоящий вход при переходе на базу.
