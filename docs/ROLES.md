# Роли и доступы

Роль отвечает на два вопроса сразу: **что можно делать** (права на модуль) и
**чьи записи видно** (зона видимости). Определения — `src/lib/rbac.ts`.

## Зоны видимости

| Зона | Что видно |
|---|---|
| `tenant` | все данные агентства |
| `branch` | только свой филиал |
| `own` | только свои контакты, лиды, сделки и задачи |

## Роли

| Роль | Зона | Суть |
|---|---|---|
| **Владелец** | агентство | всё, включая тариф, домен и удаление данных |
| **Директор** | агентство | вся операционка и аналитика; настройки без биллинга |
| **Руководитель филиала** | филиал | то же, что директор, но в пределах своего города |
| **Менеджер по продажам** | свои | лиды, квалификация, договор, передача куратору; документы своих контактов — только просмотр |
| **Куратор (оператор)** | свои | ведёт сделку: подбор вуза, документы, подача, переписка |
| **Специалист по документам** | филиал | проверка, апостиль, переводы, сроки годности |
| **Финансы** | агентство | договоры и оплаты; профили студентов — только чтение |
| **Агент-партнёр** | свои | внешний партнёр: видит только приведённых им контактов |

## Как это выражено в интерфейсе

- Навигация строится из `visibleModules(tenantId, role)` — лишних разделов
  у роли просто нет. Раздел-контейнер («CRM», «Сотрудники») остаётся в меню,
  если доступна хотя бы одна его страница.
- Кнопки действий проверяются через `allow(tenantId, role, module, action)`.
- Данные приходят из `scoped*()` — фильтр по зоне видимости стоит до рендера,
  а не прячет строки на клиенте.
- Прямой переход по ссылке на чужую запись даёт 404, а на закрытый раздел —
  понятный экран «раздел недоступен».
- Правка полей в карточке появляется только у роли с действием `edit` на этом
  разделе. Карточку сотрудника (имя, должность, телефоны, почта, день
  рождения, дата приёма) правит тот, у кого есть `team.edit`: по умолчанию
  это владелец и директор. Руководителю филиала карточки сотрудников видны,
  но не редактируются, — пока агентство не выдаст ему это право в матрице.

## Настройки закрыты кодом

Право на модуль `admin` только открывает пункт меню. Дальше стоит код
входа — один на агентство, задаётся в самом разделе. Так разведены две
разные вещи: «кому положено по роли» и «кто сейчас за клавиатурой».

Сотруднику без этого права раздела не видно вовсе: ни пункта в меню, ни
шестерёнок над доской, ни переключателя агентства в шапке. Настройка
воронки, прав, домена и тарифа физически недостижима из рабочих экранов.

## Матрица прав редактируется

«Администрирование → Права доступа» — не витрина, а рабочий экран: ячейка
«роль × раздел» открывает набор действий (просмотр, создание, изменение,
удаление, выгрузка, назначение). Изменения агентства лежат поверх ролей по
умолчанию (`effectivePermissions`) и сразу меняют и меню сотрудника, и объём
данных, которые он получает. Без права просмотра остальные действия
снимаются автоматически: раздел просто не виден.

Две страховки, которые нельзя обойти из интерфейса:

- последнего владельца агентства нельзя понизить или заблокировать — иначе
  некому вернуть доступ к тарифу и домену;
- версия продукта проверяется раньше прав: на неподключённый модуль права
  выдать нельзя, его нет в матрице.

## Что добавится

- Пользовательские роли (агентство собирает свою из набора прав).
- Передача контакта между менеджерами с сохранением истории.
- Аудит: кто открывал и менял карточку — история (`TimelineEvent`) уже пишется
  при смене стадии, правке полей, конвертации и смене роли.
